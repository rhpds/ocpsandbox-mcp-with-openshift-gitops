Converting an Existing Lab to the Sandbox API — A Real Migration Story

MCP with OpenShift: what we changed, why we changed it, and every problem we hit along the way

The MCP with OpenShift lab was originally built on the old multi-namespace Sandbox API pattern — the one that creates OCP namespaces and users directly through the API. We migrated it to the scheduler-only pattern with the new tenant roles that install on top of a cluster-provisioned base. This page is a step-by-step account of what we actually did and every problem we encountered along the way, so you do not have to figure it all out again from scratch.

1. Where We Started — The Old Pattern

Before the migration, this lab used the Sandbox API in multi-namespace mode. That meant the API was responsible for creating OCP namespaces and users as part of the order flow. Everything hung off that — identity, namespace naming, RHSSO user creation, Gitea deployment. Here is a side-by-side of where we came from and where we landed.

Old Pattern Before

  • Sandbox API in multi-namespace mode — created namespaces and OCP users directly
  • Roles named ocp4_workload_ocpsandbox_*
  • Namespace names generated by Sandbox API — less control over naming conventions
  • Keycloak user creation tied to the Sandbox API keycloak: yes tag, using RHSSO
  • Gitea: one instance per user — each order got its own full Gitea deployment (heavy)
  • ArgoCD access managed by ocp4_workload_tenant_argocd_user role per order
  • No explicit remove_workloads list — relied on reverse-order destroy
  • All infra (RHBK, Gitea, ArgoCD) installed per order, not shared across users

New Pattern After

  • Sandbox API in scheduler-only mode — just picks a cluster, nothing more
  • Roles renamed to ocp4_workload_tenant_*
  • Namespaces created by Ansible with custom naming ({suffix}-{username})
  • RHBK installed once by cluster provisioner — much newer than RHSSO and actively maintained
  • Gitea: one shared instance per cluster, one org per user (much lighter)
  • ArgoCD: shared per cluster, per-user access via gitops_bootstrap role
  • Explicit remove_workloads list for deterministic, ordered destroy
  • Three-layer architecture: cluster provisioner / platform / tenant
How big was the change? This was not a small refactor. We rewrote the AgV common.yaml, created three new Ansible roles from scratch, restructured the entire GitOps repository, and built a cluster provisioner playbook. The core logic for what the lab does stayed the same — the architecture around it changed completely.

2. Why We Migrated

The old pattern worked, but it was hitting its limits. Several things pushed us to migrate:

  • RHSSO vs RHBK. The old pattern used RHSSO through the Sandbox API keycloak: yes tag. RHSSO is the older product — RHBK is the actively maintained successor. The lab needed RHBK features, and staying on RHSSO meant we were carrying technical debt from day one.
  • Tight coupling. The ocp4_workload_ocpsandbox_* roles were built specifically for the Sandbox API namespace mode. You could not run them on an arbitrary cluster, and you could not reuse pieces of them elsewhere. The new tenant roles are cluster-agnostic.
  • No control over namespace names. The Sandbox API generated namespace names in its own format. We needed names like agent-mcpuser-guid — specific, human-readable, and consistent. You cannot get that from the API in namespace mode without a lot of workarounds.
  • One Gitea per user was unsustainable. Each order spinning up a full Gitea deployment was eating cluster resources fast. A single shared Gitea instance with per-user organizations is both lighter and easier to maintain.
  • GitOps bootstrap gives us auditable workload management. With the ArgoCD app-of-apps pattern (gitops_bootstrap), every tenant workload is declared in Git and synced by ArgoCD. Destroy is reliable. The state of any order is visible in the ArgoCD UI.
  • This is the standard going forward. The three-layer architecture (cluster provisioner + platform + tenant) is what Judd's team is standardising on for Summit 2026. Migrating now means we are building to the right pattern rather than retrofitting later.
  • Shared infra = faster orders. When RHBK, Gitea, ArgoCD, and Tekton are already installed on the cluster by the provisioner, each individual order only needs to create the per-user layer. Order time drops significantly.

3. Step-by-Step — What We Changed

These are the actual steps we took, in the order we took them. Each step is discrete enough that you could do them independently, but the dependencies flow top to bottom.

Step 1

Create the new tenant roles

We created three new roles in agnosticd/namespaced_workloads on the tenant-roles branch. These replaced the old ocp4_workload_ocpsandbox_* roles entirely.

  • ocp4_workload_tenant_keycloak_user — creates one RHBK user per order in the existing realm. Does not install RHBK — that is the cluster provisioner's job. Just calls the RHBK API to create the user with the right password and roles.
  • ocp4_workload_tenant_namespace — creates all per-user OCP namespaces with a LimitRange applied. Namespaces follow the {suffix}-{username} convention. Also creates RoleBinding entries so the tenant user has admin access in their namespaces.
  • ocp4_workload_tenant_gitea — creates a Gitea organization for the user, mirrors the GitOps repository into it, and exports the mirrored repo URL as a fact for downstream roles to consume.

Every role has both a workload.yml and a remove_workload.yml. The remove_workload.yml files mirror the creation logic in reverse — delete the RHBK user, delete the namespaces (with wait: true), delete the Gitea org.

The central username variable is ocp4_workload_tenant_keycloak_username. All three roles reference this one variable (aliased into their own _username var internally). There is one source of truth for who the user is.

We explicitly removed the old ocp4_workload_ocpsandbox_* roles from the branch rather than keeping them as dead code.

Step 2

Set up the GitOps repository structure

The ocpsandbox-mcp-with-openshift-gitops repository got a full restructure. Previously it was a flat collection of Helm charts. We reorganised it into three top-level directories that map directly to the three architectural layers: 

# Top-level directory structure after restructure
infra/
  bootstrap/          # Helm chart: creates platform/infra/tenants AppProjects in ArgoCD

platform/
  bootstrap/          # Helm chart: app-of-apps for shared cluster services (monitoring, etc.)

tenant/
  bootstrap/          # Helm chart: per-user app-of-apps (one per order)
  agent-src/          # AI agent source code — built by Tekton pipeline
  agent/              # Helm chart: deploys the agent container
  librechat/          # Helm chart: LibreChat secrets, routes, user creation job
  mcp-gitea/          # Helm chart: Gitea MCP server
  mcp-openshift/      # Helm chart: OpenShift MCP server

The key principle: each layer has its own bootstrap Application in ArgoCD, and the layers are independent. The infra/bootstrap and platform/bootstrap Applications are created by the cluster provisioner (run once per cluster). The tenant/bootstrap Application is created per order by the gitops_bootstrap Ansible role.

The infra/bootstrap chart is responsible for creating the ArgoCD AppProject resources (infra, platform, tenants) and the RBAC that controls what each project is allowed to do and which namespaces it can deploy into.

Step 3

Build the cluster provisioner

We created cluster-provision.yml — a playbook that runs once per cluster, not once per order. This is the key separation that makes the new pattern work. Everything in this playbook is cluster-wide infrastructure that will be shared across all orders.

The provisioner installs:

  • RHBK (Red Hat Build of Keycloak) via the RHBK Operator — configured with the lab realm, OAuth integration with OCP, and admin credentials
  • Gitea via the Gitea Operator — one shared instance, admin account pre-created
  • Tekton (OpenShift Pipelines) — for the agent image build pipeline
  • ArgoCD (OpenShift GitOps) — configured with the AppProject structure the lab expects
  • ToolHive — MCP proxy infrastructure
  • CloudNativePG — PostgreSQL operator for LibreChat's database

The provisioner calls ocp4_workload_gitops_bootstrap twice: once for infra/bootstrap and once for platform/bootstrap. This was also when we extended the gitops_bootstrap role to support an ocp4_workload_gitops_bootstrap_applications list — so a single role invocation can create multiple ArgoCD Applications in one shot.

We also added RBAC and AppProject creation to the infra bootstrap layer so that when the tenant/bootstrap Application is created later (per order), it is already operating inside a project that has appropriate permissions.

When does the provisioner run? The cluster provisioner runs once, manually, on each assigned sandbox cluster before it is made available for orders. For this lab we provisioned cnv-us-east-ocp-3 and validated the full stack before placing test orders.
Step 4

Rewrite AgV common.yaml

This was the most visible part of the migration — the AgV common.yaml for the MCP with OpenShift catalog item changed substantially. Here is what changed and why.

Sandbox entry — from multi-namespace to scheduler-only:

# Old pattern — multi-namespace mode
sandbox_api:
  namespaces:
    - namespace_suffix: agent
    - namespace_suffix: librechat
    - namespace_suffix: mcp
  keycloak: yes

# New pattern — scheduler-only mode
sandbox_api:
  - kind: OcpSandbox
    alias: cluster
    cloud_selector:
      mcp_ready: true

Workloads list — replaced old roles with new tenant roles:

workloads:
  - ocp4_workload_tenant_keycloak_user
  - ocp4_workload_tenant_namespace
  - ocp4_workload_tenant_gitea
  - ocp4_workload_gitops_bootstrap

remove_workloads:
  - ocp4_workload_gitops_bootstrap
  - ocp4_workload_tenant_gitea
  - ocp4_workload_tenant_namespace
  - ocp4_workload_tenant_keycloak_user

Key variables added:

# Deterministic password derived from guid — same GUID always gets the same password
common_password: "Mcp{{ (guid | hash('sha256'))[:8] }}!"

# Central username — all roles and the bootstrap chart reference this one variable
ocp4_workload_tenant_keycloak_username: "mcpuser-{{ guid }}"

# Namespace username alias — tenant_namespace role reads this
ocp4_workload_tenant_namespace_username: "{{ ocp4_workload_tenant_keycloak_username }}"

We also added the cloud_selector tags to restrict which clusters get assigned. Only clusters labelled mcp_ready: true in the Sandbox API inventory are eligible — those are the ones with the cluster provisioner already run on them.

Step 5

Wire the GitOps bootstrap Helm values

The gitops_bootstrap role does more than create an ArgoCD Application. It also passes Helm values into the tenant/bootstrap/ chart. Those values flow through the bootstrap chart into every individual tenant ArgoCD Application (LibreChat, agent, MCP servers, etc.).

Getting this data flow right was the most time-consuming part of the whole migration. The key values that needed to pass through:

  • tenant.username — the RHBK / OCP username (mcpuser-{{ guid }})
  • tenant.password — the common_password value
  • deployer.domain — the cluster's base domain (e.g. apps.cnv-us-east-ocp-3.example.com)
  • litemaas.url, litemaas.key, litemaas.models — LiteMaaS endpoint and credentials

LiteMaaS credentials in particular follow a long chain: AgV sets them as AgnosticD variables, the gitops_bootstrap role picks them up via ocp4_workload_gitops_bootstrap_helm_values, they are written into the bootstrap Application's Helm values, and the tenant/bootstrap/ chart templates them out as parameters into each child Application's Helm values.

If any link in that chain is broken — a typo in a variable name, a missing | quote in a template, a YAML list rendered as a string — the downstream application will either fail to sync or start with the wrong configuration.

Step 6

Add cascade finalizer and remove_workload to gitops_bootstrap

Destroy was an afterthought in the old pattern. In the new pattern, we designed it explicitly. The mechanism is ArgoCD's cascade finalizer.

When we create the tenant/bootstrap Application, we add the resources-finalizer.argocd.argoproj.io finalizer to its metadata. This tells ArgoCD: when this Application is deleted, cascade-delete all child Applications and all resources they manage before completing the deletion. 

# In the bootstrap Application template
metadata:
  name: "tenant-bootstrap-{{ guid }}"
  namespace: openshift-gitops
  finalizers:
    - resources-finalizer.argocd.argoproj.io

When gitops_bootstrap's remove_workload.yml runs, it deletes the bootstrap Application. ArgoCD picks up the deletion, sees the cascade finalizer, and works down the tree: deletes each child Application, which triggers deletion of all Kubernetes resources in each child Application, which eventually results in all tenant workloads being gone.

The namespace is deleted only after ArgoCD confirms the cascade is complete. This avoids the stuck-terminating-namespace problem that plagued the old pattern, where namespaces would get stuck because resources inside them still had finalizers.

Step 7

Validate end-to-end

Once all the pieces were in place, we ran end-to-end validation on the assigned cluster (cnv-us-east-ocp-3). We placed five test orders and validated each one:

  • GUIDs used: drw4x, 9b87v, lvs9k, 7gb7l, d7tjs
  • RHBK login — confirmed user could authenticate and OCP SSO worked
  • LibreChat — confirmed app loaded, user could log in with common_password, models listed correctly from LiteMaaS
  • Showroom — confirmed lab guide rendered
  • MCP servers — confirmed ToolHive proxied both Gitea and OpenShift MCP servers
  • ArgoCD sync — confirmed all Applications showed Synced / Healthy
  • Destroy — ran destroy for each GUID and confirmed namespaces cleaned up, RHBK user deleted, Gitea org removed

Not all of these passed on the first attempt. The next section covers every failure we hit.

4. Challenges and How We Solved Them

These are the actual problems we hit, in roughly the order we encountered them. Each one cost us real time — hopefully reading about them costs you less.

Challenge 1: $password undefined in Helm bootstrap template

Symptom: LibreChat's user creation job was running, but it was using user1@example.com as the email and a placeholder string as the password. Users could not log in.

Root cause: The $password variable was never defined in the Helm template. The tenant/bootstrap/templates/applications.yaml template was passing default_user values into the LibreChat Application's Helm parameters, but it was constructing them from hardcoded strings rather than reading tenant.password from the values file. The variable reference simply did not exist.

Fix: Added a variable definition at the top of tenant/bootstrap/templates/applications.yaml: 
{{- $username := .Values.tenant.username | default "" }}
{{- $password := .Values.tenant.password | default "" }}
Then referenced them in the LibreChat Application's Helm parameters: 
- name: default_user.email
  value: "{{ $username }}@example.com"
- name: default_user.password
  value: "{{ $password }}"

Challenge 2: LibreChat secrets showing "FROM SECRETS" placeholders

Symptom: LibreChat would not start. The pod logs showed it trying to read creds_key, jwt_secret, and meili_master_key from environment variables, but those variables were set to literal placeholder strings like FROM_SECRETS. The app refused to boot with placeholder values.

Root cause: The LibreChat Helm chart expected these secrets to exist in a Kubernetes Secret resource that would be pre-created. The bootstrap template was generating the Application but not generating actual values for these secrets. They ended up as placeholders because nothing had created the Secret with real values.

Fix: We used Helm's sha256sum function to generate deterministic secret values from the username. This means the same username always generates the same secrets — consistent across re-provisions: 
creds_key: {{ sha256sum $username | quote }}
jwt_secret: {{ sha256sum (printf "%s-jwt" $username) | quote }}
meili_master_key: {{ sha256sum (printf "%s-meili" $username) | trunc 16 | quote }}
meili_master_key has a 16-character minimum and maximum in MeiliSearch — hence the trunc 16. These values are written directly into the bootstrap chart's output, which becomes a Secret applied by ArgoCD.

Challenge 3: OCP login "Invalid client credentials" after cluster re-provision

Symptom: After we re-ran the cluster provisioner on cnv-us-east-ocp-3 to fix a configuration issue, existing and new users could no longer log in to OCP via RHBK. The browser showed "Invalid client credentials" at the OAuth callback.

Root cause: The cluster provisioner regenerated the OAuth client secret for the RHBK identity provider in OCP's OAuth configuration. The oauth-openshift pods in the openshift-authentication namespace load OAuth configuration at startup — they do not hot-reload it. So the pods were still using the old client secret from the previous provisioner run, while RHBK was now expecting the new one.

Fix: Restart the oauth-openshift pods after any cluster provisioner run that touches OAuth configuration: 
# Force a rolling restart of the oauth pods
oc rollout restart deployment/oauth-openshift -n openshift-authentication
oc rollout status deployment/oauth-openshift -n openshift-authentication
This is documented OCP behavior — any time the OAuth custom resource changes (including the IdP client secret), the pods must be restarted to pick up the new config. We added this as a task at the end of cluster-provision.yml so it happens automatically.

Challenge 4: git_url undefined when gitops_bootstrap ran

Symptom: The ocp4_workload_gitops_bootstrap role failed with a variable undefined error for ocp4_workload_gitops_bootstrap_repo_url. The role could not create the ArgoCD Application because it did not know which repo URL to point it at.

Root cause: The repo URL is supposed to come from the ocp4_workload_tenant_gitea role, which mirrors the GitOps repo into the tenant's Gitea organization and knows the resulting URL. But the variable name that tenant_gitea was setting as a fact did not match what gitops_bootstrap was looking for. The fact was being set but under a different name, so it was effectively invisible to the consuming role.

Fix: Updated ocp4_workload_tenant_gitea's workload.yml to explicitly set the fact using the exact variable name that gitops_bootstrap expects: 
- name: Set GitOps repo URL fact for downstream roles
  ansible.builtin.set_fact:
    ocp4_workload_gitops_bootstrap_repo_url:
      "https://gitea.{{ ocp4_workload_tenant_gitea_domain }}/{{ ocp4_workload_tenant_gitea_username }}/mcp.git"
AgV no longer needs to set ocp4_workload_gitops_bootstrap_repo_url manually. It flows automatically from tenant_gitea to gitops_bootstrap as a runtime fact. This is cleaner and means AgV does not need to know how Gitea constructs URLs.

Challenge 5: Namespace role failing with undefined username

Symptom: ocp4_workload_tenant_namespace failed early in the run with a task-level undefined variable error. The role could not determine what username to use when naming namespaces or creating RoleBinding resources.

Root cause: The role was internally looking for a variable called ocp4_workload_tenant_username. AgV was setting ocp4_workload_tenant_keycloak_username. These are different names. The role never found the variable because the names did not match, and there was no default or alias defined.

Fix: Renamed the role's internal variable to the role-namespaced form ocp4_workload_tenant_namespace_username (following the convention that role variables are prefixed with the role name). Then mapped it in AgV: 
# In AgV common.yaml
ocp4_workload_tenant_keycloak_username: "mcpuser-{{ guid }}"
ocp4_workload_tenant_namespace_username: "{{ ocp4_workload_tenant_keycloak_username }}"
This explicit mapping in AgV makes the dependency clear. The namespace role does not reach outside its own variable namespace, and AgV is the place that says "these two things refer to the same user."

Challenge 6: LibreChat models list rendered as a comma string, not a YAML list

Symptom: LibreChat started but the model selector showed nothing — or showed one item that was a single comma-separated string like mistral-7b,llama3-8b,mixtral-8x7b instead of three separate models. LibreChat's config parser rejected the malformed list.

Root cause: LiteMaaS model names are stored in AgV as a single comma-separated string: litemaas_models: "mistral-7b,llama3-8b,mixtral-8x7b". The bootstrap template was passing this string directly into the LibreChat configYaml block without splitting it. Helm rendered it as a scalar string, not a YAML list. LibreChat's config parser could not use it.

Fix: Used Helm's splitList function in the bootstrap template to split the comma-separated string and render each model as a YAML list item: 
{{- $models := .Values.litemaas.models | default "" }}
models:
  default:
{{- range splitList "," $models }}
    - {{ . | trim | quote }}
{{- end }}
The trim call handles any whitespace around model names in the comma-separated value. LibreChat now receives a properly formatted YAML list.

Challenge 7: LibreChat crashing with permission error on log directory

Symptom: The LibreChat pod entered CrashLoopBackOff immediately on startup. The container logs showed: mkdir /app/logs/: permission denied and the same for /app/api/logs.

Root cause: The LibreChat container image tries to create log directories at /app/api/logs and /app/logs during startup. OpenShift's default Security Context Constraints prevent containers from writing to arbitrary filesystem paths — the container image was built assuming it would run with write access to /app, but OpenShift's SCC does not allow that.

Fix: Added emptyDir volume mounts for both log paths in the LibreChat Helm values passed through the bootstrap chart. An emptyDir is always writable, satisfies the container's need to create log files, and is ephemeral — logs go away when the pod restarts, which is acceptable for this lab: 
volumes:
  - name: logs
    emptyDir: {}
  - name: logs-root
    emptyDir: {}
volumeMounts:
  - name: logs
    mountPath: /app/api/logs
  - name: logs-root
    mountPath: /app/logs

Challenge 8: GitOps repo URL hardcoded vs dynamic

Symptom: ArgoCD Applications were syncing correctly, but from the wrong source. Inspection of the tenant Application in the ArgoCD UI showed it was pointing to github.com/rhpds/ocpsandbox-mcp-with-openshift-gitops — the public GitHub repo — instead of the tenant's private Gitea mirror. This meant ArgoCD was not reading from the user's isolated copy.

Root cause: Early versions of the tenant/bootstrap/ chart template had the repo URL hardcoded to the GitHub origin. When we added Gitea mirroring, we updated the tenant_gitea role but forgot to update the bootstrap chart template to use the dynamic Gitea URL. The chart was still referencing the old static value.

Fix: The bootstrap template now derives the repo URL from tenant.username and deployer.domain, which are both passed in as Helm values: 
{{- $username := .Values.tenant.username }}
{{- $domain := .Values.deployer.domain }}
# Repo URL used in each Application's source:
repoURL: "https://gitea-gitea-{{ $username }}.{{ $domain }}/{{ $username }}/mcp.git"
Every tenant's ArgoCD Applications now point to that tenant's specific Gitea-hosted mirror of the GitOps repo. Changes to the bootstrap chart are deployed to tenants only after they are reflected in the mirror — which is the intended isolation model.

Challenge 9: Namespace format changed mid-migration

Symptom: Namespace names were inconsistent between test orders. Some namespaces were named agent-mcpuser-drw4x (suffix-first), others were mcpuser-9b87v-agent (username-first). ArgoCD AppProject namespace restrictions were not matching both patterns, causing sync failures on some orders.

Root cause: The naming convention changed during development. The initial version of ocp4_workload_tenant_namespace used {username}-{suffix} ordering (username-first). During a refactor, we switched to {suffix}-{username} (suffix-first) because it made namespaces easier to read when sorted in oc get ns. But we did not update all role variables and ArgoCD configuration at the same time.

Fix: Standardised on {suffix}-{username} format across all roles and all Helm chart references. Updated the ArgoCD AppProject for the tenants project to use a wildcard * in the namespace field instead of a specific pattern: 
destinations:
  - server: 'https://kubernetes.default.svc'
    namespace: '*'  # Accept any namespace — project RBAC controls actual access
Using * for the tenants AppProject is intentional: we control access through namespace RoleBinding resources applied by the tenant_namespace role, not through AppProject destination restrictions.

5. Key Lessons Learned

  1. Define the username variable once and reference it everywhere. We lost time because different roles expected different variable names for what was the same concept: the user's identity. The fix was ocp4_workload_tenant_keycloak_username as the single source of truth in AgV, with each role aliasing it into its own _username variable internally. Any time you find yourself copy-pasting a username value into multiple role variables, stop and make one variable that all the others derive from.
  2. Use a deterministic password formula from the start. Generating common_password from sha256(guid)[:8] means you can re-provision the same GUID and always get the same password. This was invaluable during testing — we re-ran provisioner steps many times on the same test GUIDs and never had to track down what password was currently set. If your password is truly random per run, you will spend a lot of time resetting it during debugging.
  3. Separate cluster provisioner from per-order provisioning early. Mixing cluster-wide setup (RHBK, Gitea, ArgoCD) with per-order tenant logic creates a situation where everything depends on everything else and nothing is clearly owned. Once we put cluster-wide infra into cluster-provision.yml and per-order logic into the tenant roles, the design became much cleaner. Each piece had a clear owner, a clear input, and a clear output.
  4. Test destroy as often as you test provision. We found most cleanup bugs only when we ran destroy for the first time against a fully working environment. Namespaces stuck in Terminating, Gitea orgs not deleted, RHBK users left behind — all of these showed up in destroy runs, not provision runs. After the first full cycle, run destroy immediately. Fix what breaks. Then provision again. Treat destroy as a first-class test case, not an afterthought.
  5. ArgoCD namespace must pre-exist. ArgoCD on a shared cluster will not create a namespace for you as part of a sync. If the Application's destination.namespace does not exist, the sync fails. Ansible creates the namespace and applies RBAC first; ArgoCD then syncs workloads into the already-existing namespace. If you reverse this order, the sync fails with permission errors that can be confusing to diagnose because the error message does not always say "namespace does not exist."
  6. The bootstrap chart is the glue layer — get it right first. The tenant/bootstrap/ Helm chart is what connects AgV variables (via gitops_bootstrap Helm values) to all the individual tenant ArgoCD Applications. It is the most important single piece of the new architecture. Every variable that needs to flow to LibreChat, the agent, or an MCP server goes through this chart. Getting the template logic right — especially secret generation, list rendering, and value passing — took more iteration than any other single component. Plan to spend time here.
  7. OCP OAuth pod restart is required after IdP changes. Any time the cluster provisioner changes the OCP OAuth configuration — registering a new RHBK client, changing the client secret, adding a new identity provider — the oauth-openshift pods in openshift-authentication must be restarted manually (or via an Ansible task at the end of the provisioner). OCP does not hot-reload OAuth config. Build this restart into your provisioner as a standard final step.
  8. Pin collection branches during development. Using version: main for all AgnosticD collections means any unrelated role change on main can break your lab silently. During active development, pin to a specific branch. Once the lab is stable and merged, agree on a tagging strategy so you know exactly what version of each collection your lab is running against.
