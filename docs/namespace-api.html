How It Works

In the Full Namespace API pattern, Sandbox API takes on more responsibility than in the Scheduler-Only pattern. For every order, Sandbox API:

  1. Selects a cluster from the pool (same as Scheduler-Only)
  2. Creates one OCP namespace per entry in your sandboxes: list — the namespace name is generated from the catalog name, the entry suffix, and the order GUID
  3. Creates an OCP local user account (sandbox_username) with a generated password (sandbox_password)
  4. Grants the user edit access to the primary namespace
  5. Applies resource quota to each namespace based on your AgV quota variables
  6. Injects all the sandbox variables (namespace names, user credentials, cluster URLs, SA token) into the AgnosticD run
  7. On destroy: deletes the namespaces (and all in-namespace resources) and the OCP user account

Your Ansible roles then deploy lab content directly into the ready-made namespaces. You do not need a ocp4_workload_tenant_namespace role — that work has already been done.

When to Use This Pattern

Choose the Full Namespace API pattern when your lab meets most of these criteria:

Good fit

  • Each order gets its own isolated namespace(s)
  • You want Sandbox API to own namespace and user lifecycle
  • Your lab deploys into namespaces (not cluster-wide resources)
  • No shared cluster services required (no dedicated Keycloak/Gitea instance)
  • OCP local user authentication is sufficient (no SSO required)
  • You prefer simpler AgV configuration with fewer roles
  • Single-team or single-namespace lab topology
  • Short or medium duration labs where cluster lifecycle is straightforward

Poor fit — use Scheduler-Only instead

  • Multiple tenants sharing one cluster with complex isolation requirements
  • Need Keycloak/RHBK SSO (not OCP local user)
  • Need per-tenant Gitea org and repo mirroring
  • Need ArgoCD GitOps managing tenant workloads
  • Need LiteMaaS AI API keys per tenant
  • Need 5+ namespaces per tenant with custom naming
  • Cluster-wide resources that must be managed per-tenant
Simpler operation, less flexibility The Full Namespace API pattern requires fewer Ansible roles and less AgV configuration. The tradeoff is that you get what Sandbox API creates — OCP local users, standard namespace names, and basic quota. You cannot customize SSO, namespace topology, or service topology at the cluster level.

Complete AgV common.yaml — Annotated

The following is a complete, production-ready common.yaml for the Full Namespace API pattern. It shows a two-namespace setup (primary user namespace + secondary tools namespace) with Showroom. Adapt the role names and variables for your specific catalog item.

Namespace naming convention Namespace names are generated as <catalog-item-name>-<namespace_suffix>-<guid>. The catalog item name comes from the AgV catalog directory name. For example, if your catalog item is mylab and the suffix is user, the namespace will be mylab-user-abc12. 
---
# ============================================================
# AgnosticV — common.yaml
# Pattern: Full Namespace API
# The Sandbox API creates namespaces AND OpenShift users.
# Simpler for labs that deploy into sandbox-managed namespaces.
# ============================================================

# ── 1. SANDBOX ENTRIES ───────────────────────────────────────
# One entry per namespace you need.
# namespace_suffix determines the namespace name: <catalog>-<suffix>-<guid>
# Example with catalog name "mylab":
#   mylab-user-abc12   ← primary namespace (sandbox_openshift_namespace)
#   mylab-tools-abc12  ← secondary namespace
sandboxes:
  - name: user         # Primary namespace — vars prefixed with sandbox_openshift_*
    namespace_suffix: user
  - name: tools        # Additional namespace — vars prefixed with sandbox_openshift_tools_*
    namespace_suffix: tools

# Sandbox API automatically creates and provides:
#   sandbox_openshift_namespace        = "mylab-user-<guid>"
#   sandbox_openshift_api_url          = "https://api.cluster-xyz.example.com:6443"
#   sandbox_openshift_ingress_domain   = "apps.cluster-xyz.example.com"
#   sandbox_openshift_console_url      = "https://console-openshift-console..."
#   cluster_admin_agnosticd_sa_token   = "<SA JWT token — never log or commit this>"
#   sandbox_username                   = "user-<guid>"    ← OCP user created by sandbox API
#   sandbox_password                   = "<password>"      ← from RHDP vault
#   sandbox_openshift_tools_namespace  = "mylab-tools-<guid>"  ← second namespace

# ── 2. WORKLOAD ORDER ────────────────────────────────────────
# Sandbox API has already created the namespaces and OCP user.
# Your roles just deploy into them.
workloads:
  - my_collection.ocp4_workload_my_lab_setup    # Deploy your lab resources
  - agnosticd.showroom.ocp4_workload_showroom    # Showroom tab UI (optional)

# ── 3. ROLE CONFIGURATION ────────────────────────────────────
# Use the sandbox-provided variables directly.
# No need for ocp4_workload_tenant_* roles — sandbox API did that work.
my_lab_setup_namespace: "{{ sandbox_openshift_namespace }}"
my_lab_setup_username: "{{ sandbox_username }}"
my_lab_setup_password: "{{ sandbox_password }}"
my_lab_setup_api_url: "{{ sandbox_openshift_api_url }}"
my_lab_setup_ingress_domain: "{{ sandbox_openshift_ingress_domain }}"

# Secondary namespace (if you declared it in sandboxes above)
my_lab_setup_tools_namespace: "{{ sandbox_openshift_tools_namespace }}"

# ── 4. QUOTA ─────────────────────────────────────────────────
# Sandbox API applies quota to the namespace it creates.
# Set these vars to control resource limits for this catalog item.
quota_requests_cpu: "4"
quota_requests_memory: 8Gi
quota_limits_cpu: "8"
quota_limits_memory: 16Gi
quota_pods: "50"

# ── 5. SHOWROOM ──────────────────────────────────────────────
# Use sandbox-provided vars to build the tab URLs.
showroom_git_repo: "https://github.com/myorg/my-lab-showroom.git"
showroom_git_repo_revision: main
showroom_user_data:
  username: "{{ sandbox_username }}"
  password: "{{ sandbox_password }}"
  console_url: "{{ sandbox_openshift_console_url }}"
  namespace: "{{ sandbox_openshift_namespace }}"
  app_url: "https://myapp-{{ sandbox_openshift_namespace }}.{{ sandbox_openshift_ingress_domain }}"

# ── 6. DESTROY ORDER ─────────────────────────────────────────
# Sandbox API automatically deletes the namespaces and OCP user.
# Only destroy what you created that is NOT inside a namespace.
# (In-namespace resources are auto-deleted when the namespace is deleted.)
remove_workloads:
  - agnosticd.showroom.ocp4_workload_showroom
  - my_collection.ocp4_workload_my_lab_setup
# Note: sandbox API deletes the namespaces — no tenant_namespace role needed.

2. workloads workloads: Only your lab-specific roles and Showroom. You do not need ocp4_workload_tenant_namespace, ocp4_workload_tenant_keycloak_user, or ocp4_workload_tenant_gitea — Sandbox API handled those concerns.

All Sandbox API Variables — Full Reference

Primary namespace variables (always provided)

These variables are always injected when you have at least one sandbox entry with a namespace_suffix. They correspond to the first (primary) sandbox entry.

Variable Example value Description
sandbox_openshift_namespace mylab-user-abc12 The primary namespace created by Sandbox API. Format: <catalog-name>-<suffix>-<guid>. This is the namespace your main lab resources should be deployed into.
sandbox_openshift_api_url https://api.cluster-abc12.example.com:6443 The OpenShift cluster API endpoint. Used by k8s Ansible modules and oc CLI. Same value for all sandbox entries in a given order (they all land on the same cluster).
sandbox_openshift_ingress_domain apps.cluster-abc12.example.com The wildcard ingress domain for the cluster. Use this to construct Route hostnames and application URLs. E.g., myapp-{{ sandbox_openshift_namespace }}.{{ sandbox_openshift_ingress_domain }}.
sandbox_openshift_console_url https://console-openshift-console.apps.cluster-abc12.example.com The full URL to the OpenShift web console. Pass this to Showroom user_data for lab attendees to access the console directly from a tab.
cluster_admin_agnosticd_sa_token eyJhbGciOiJSUzI1NiIs... A cluster-admin scoped SA token for AgnosticD. Used internally for all Kubernetes API calls. Never log this variable. Never reference it in your own role variables. Never commit it.
sandbox_username user-abc12 The OCP local user account created by Sandbox API for this order. The user is granted edit access to the primary namespace. Provide this to the lab attendee as their login username.
sandbox_password (generated, from RHDP vault) The password for sandbox_username. Generated by RHDP's secret management system — never hardcode this. Pass it to Showroom user_data for display to the attendee.

Additional namespace variables (per extra sandbox entry)

For every sandbox entry after the first (entries with a name other than the primary), Sandbox API provides a namespace variable prefixed with the entry's name.

sandbox entry name Variable provided Example value
tools sandbox_openshift_tools_namespace mylab-tools-abc12
db sandbox_openshift_db_namespace mylab-db-abc12
monitoring sandbox_openshift_monitoring_namespace mylab-monitoring-abc12
pipeline sandbox_openshift_pipeline_namespace mylab-pipeline-abc12
Variable naming pattern The pattern is always: sandbox_openshift_<name>_namespace where <name> is the value of the name: key in your sandbox entry. The first entry's namespace uses the short form sandbox_openshift_namespace (no name infix).

The guid variable

Variable Example Notes
guid abc12 5-character unique identifier for this order. Injected by AgnosticD, not Sandbox API. It appears in all generated names: namespace names, username, etc. Use it when you need to derive unique names not already provided by sandbox vars.

What Sandbox API Handles vs. What You Handle

Sandbox API handles automatically

  • Namespace creation (one per sandbox entry)
  • Namespace naming (<catalog>-<suffix>-<guid>)
  • OCP local user creation (sandbox_username)
  • User password generation (sandbox_password)
  • Granting user edit access to the primary namespace
  • Applying ResourceQuota based on quota vars
  • Cluster-admin SA token creation and injection
  • Cluster URL and ingress domain injection
  • On destroy: namespace deletion (cascade deletes all in-namespace resources)
  • On destroy: OCP user account deletion
  • On destroy: SA token revocation
  • On destroy: cluster returned to pool

You handle (via AgnosticD roles)

  • Deploying your lab application into the provided namespaces
  • Any cluster-scoped resources your lab needs (use sparingly)
  • Showroom tab UI configuration and deployment
  • Any resources that live outside the sandbox-provided namespaces
  • LiteMaaS virtual keys (if your lab uses AI APIs)
  • Any external service integrations (webhooks, external registries, etc.)
  • On destroy: cleaning up any resources you created outside the sandbox namespaces
In-namespace resources are automatically cleaned up When Sandbox API deletes a namespace on destroy, all Kubernetes resources inside it (Deployments, Services, Routes, PVCs, Secrets, ConfigMaps, etc.) are deleted automatically by OpenShift. Your remove_workloads only needs to handle resources that exist outside those namespaces, or resources that require explicit API calls to external systems (like revoking an API key).

Decision rule of thumb If your lab needs an OCP user to log into the console and deploy something into one or two namespaces, use Full Namespace API. If your lab needs SSO, per-tenant Gitea repos, ArgoCD, and LiteMaaS AI keys all wired together, use Scheduler-Only.

Quota and Destroy Notes

Quota configuration

Sandbox API reads a standard set of quota variables and applies a ResourceQuota to each namespace it creates. Set these variables in your AgV common.yaml to control how much cluster capacity each order consumes.

Variable Default (if unset) Recommended range for typical labs
quota_requests_cpu 2 "2" – "8" depending on workload
quota_requests_memory 4Gi 4Gi – 16Gi
quota_limits_cpu 4 Should be 2x requests
quota_limits_memory 8Gi Should be 2x requests
quota_pods 25 "25" – "100"
Quota applies per namespace, per sandbox entry If you have two sandbox entries (e.g., user and tools), the quota is applied independently to each namespace. An order with two namespace entries will consume up to 2x the declared quota from the cluster's total capacity. Size accordingly.

Destroy behavior

When an order is destroyed, the sequence is:

  1. AgnosticD runs remove_workloads — your roles clean up external resources (e.g., revoke an API key, remove a webhook, delete a Showroom deployment)
  2. Sandbox API deletes all namespaces for this order — all in-namespace Kubernetes resources are cascade-deleted automatically by OpenShift
  3. Sandbox API deletes the OCP user account (sandbox_username)
  4. Sandbox API revokes the cluster-admin SA token used by AgnosticD
  5. Sandbox API returns the cluster to the pool (or schedules cluster retirement)
Keep remove_workloads short Because Sandbox API handles namespace and user deletion, your remove_workloads list should only include roles that created resources outside the sandbox namespaces, or roles (like Showroom) that need an explicit API call to clean up. Do not replicate what Sandbox API already handles.
PVC data is permanently lost on destroy PersistentVolumeClaims inside sandbox namespaces are deleted with the namespace. There is no backup. If your lab requires data persistence across sessions or restarts, you must design for it explicitly (e.g., use an external object store, or document that data is ephemeral).

Important notes

  • Do not create cluster-scoped resources (ClusterRoles, ClusterRoleBindings, CRDs, etc.) unless absolutely necessary — they are not automatically cleaned up when the namespace is deleted and can accumulate across orders
  • LimitRange: Sandbox API also applies a LimitRange with default container CPU/memory limits. This means containers without explicit resource requests will inherit these defaults. Design your workloads with this in mind.
  • sandbox_password security: The sandbox password is managed by RHDP's vault system. Never log it, never store it in a ConfigMap or Secret that persists beyond the lab session, and never commit it to Git.
  • cluster_admin_agnosticd_sa_token security: This token has full cluster-admin access. It is used exclusively by AgnosticD internally. Do not pass it to your role variables or use it in templates.
