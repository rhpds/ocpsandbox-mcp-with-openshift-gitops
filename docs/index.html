What is Sandbox API?

Sandbox API is the RHDP service that allocates OpenShift clusters (and other cloud resources) to lab orders. When a user requests a catalog item, the RHDP platform calls Sandbox API to provision a cluster from a pre-warmed pool, then hands control to AgnosticD (via AgnosticV configuration) to deploy the actual lab content.

Sandbox API does the following for every order:

  • Picks an available OpenShift cluster from the resource pool
  • Creates a service account with cluster-admin privileges for AgnosticD to use
  • Injects a set of well-known variables into your AgnosticD run (API URL, ingress domain, console URL, SA token)
  • Optionally creates namespaces and OCP user accounts (Full Namespace API pattern only)
  • Reclaims the cluster when the order is destroyed or expired

Sandbox API does not deploy your lab content. That is the job of AgnosticD roles configured through AgnosticV. The two patterns described in this guide differ in how much Sandbox API does versus how much your Ansible roles do.

Key insight In both patterns your AgnosticV common.yaml configures which Ansible roles run, in what order, and with what variables. Sandbox API just gives you a cluster and injects variables. Everything else is Ansible.

Three-Layer Architecture: Infra / Platform / Tenant

The Scheduler-Only pattern is built on a three-layer architecture. Each layer has a clear owner, runs at a different frequency, and has a different lifecycle. Understanding this separation is essential before writing any AgV configuration.

Layer Runs Who triggers it Destroyed when? Key components
Infra Once per cluster cluster-provision.yml — run by operator when cluster is onboarded to the pool Never (cluster is retired) RHBK, Gitea operator, ArgoCD, Tekton, ToolHive, AppProjects
Platform Once per cluster ArgoCD (bootstrap-platform) — triggered by infra bootstrap Never (cluster is retired) User workload monitoring, future shared services
Tenant Every order AgnosticD roles via AgV workloads: list Order ends — each role's remove_workload.yml runs RHBK user, namespaces, Gitea instance, LibreChat, MCP servers, agent
Only the Tenant layer is in your AgV common.yaml The Infra and Platform layers are set up once by the cluster operator — they are not part of your catalog item configuration. When you write a workloads: list in AgV, you are only configuring the Tenant layer. The shared infrastructure is already there waiting.

Which Pattern Should I Use?

There are two integration patterns. Choose based on who should own namespace and user lifecycle.

Scheduler-Only Summit 2026

Use when

  • Multiple tenants share one cluster
  • A cluster provisioner pre-installs shared services (Keycloak, Gitea, ArgoCD) once
  • Your Ansible roles create namespaces and users per-order
  • You need GitOps (ArgoCD) managing tenant workloads
  • You need LiteMaaS AI API keys per tenant
  • Complex multi-namespace topologies per tenant

Sandbox API does: Schedule cluster, provide token + domain

Your roles do: Create users, namespaces, repos, ArgoCD apps, everything else

Full Namespace API

Use when

  • Each order gets its own isolated namespace(s)
  • You want Sandbox API to own namespace + OCP user lifecycle
  • Simpler labs that deploy directly into sandbox namespaces
  • No shared cluster services needed
  • Single-team or single-namespace workloads
  • Less Ansible role complexity is acceptable

Sandbox API does: Schedule cluster, create namespaces, create OCP user, apply quota

Your roles do: Deploy lab content into the ready namespaces

Summit 2026 — Scheduler-Only Pattern

In the Scheduler-Only pattern, Sandbox API does the minimum: it schedules a cluster from the pool and gives your AgnosticD run the cluster credentials. All per-tenant resources (namespaces, Keycloak users, Gitea orgs, ArgoCD applications) are created by Ansible roles on every order.

A separate cluster provisioner playbook (not in AgV) runs once per cluster to install shared services: Red Hat Build of Keycloak (RHBK), Gitea, OpenShift GitOps (ArgoCD), and LiteMaaS. Once the cluster is provisioned, it accepts tenant orders until it reaches capacity.

Important: Three-layer architecture The cluster provisioner runs once. The platform layer may also run once. Each order runs the tenant Ansible roles. Do not confuse these layers — they are separate playbooks with separate scopes.

Minimal AgV sandboxes entry

# Scheduler-Only: single entry under __meta__
# Sandbox API schedules a cluster and provides credentials.
# It does NOT create namespaces or users — Ansible roles do that.
__meta__:
  sandboxes:
  - kind: OcpSandbox
    alias: cluster
    namespace_suffix: user       # scheduling artifact — not used by your roles
    cloud_selector:
      cloud: cnv-dedicated-shared
      demo: my-lab
      purpose: prod
    quota:
      limits.cpu: "2"
      requests.cpu: "2"
      limits.memory: 4Gi
      requests.memory: 4Gi

# Sandbox API provides:
#   sandbox_openshift_api_url        — cluster API endpoint
#   sandbox_openshift_ingress_domain — wildcard apps domain
#   sandbox_openshift_console_url    — web console URL
#   cluster_admin_agnosticd_sa_token — cluster-admin SA token

Minimal workloads list

workloads:
  - agnosticd.namespaced_workloads.ocp4_workload_tenant_keycloak_user
  - agnosticd.namespaced_workloads.ocp4_workload_tenant_namespace
  - agnosticd.namespaced_workloads.ocp4_workload_tenant_gitea
  - agnosticd.ai_workloads.ocp4_workload_litellm_virtual_keys
  - agnosticd.core_workloads.ocp4_workload_gitops_bootstrap
  - agnosticd.showroom.ocp4_workload_showroom

Full Namespace API Pattern

In the Full Namespace API pattern, each sandbox entry in your AgV sandboxes: list causes Sandbox API to create one namespace and one OCP user account. Your Ansible roles then deploy lab content directly into those ready-made namespaces using the sandbox-provided variables.

This pattern is simpler to operate: there is no cluster provisioner, no Keycloak role, no Gitea role. The tradeoff is less flexibility — you get whatever Sandbox API creates, not a fully custom per-tenant environment.

AgV sandboxes entry for two namespaces

# Full Namespace API: one entry per namespace under __meta__
# alias + cluster_condition: same() ensures both namespaces
# land on the SAME cluster — without this they can end up on different clusters.
__meta__:
  sandboxes:
  - kind: OcpSandbox
    alias: primary
    namespace_suffix: user       # → sandbox-<guid>-user
    cloud_selector:
      cloud: cnv-dedicated-shared
      demo: my-lab
      purpose: prod
      keycloak: "yes"              # creates RHSSO user (sandbox_username/password)
    quota:
      limits.cpu: "10"
      requests.memory: 20Gi
  - kind: OcpSandbox
    alias: tools
    var: sandbox_tools             # sets Ansible variable prefix for this entry
    namespace_suffix: tools       # → sandbox-<guid>-tools
    cluster_condition: same('primary')   # MUST be on the same cluster as primary
    cloud_selector:
      cloud: cnv-dedicated-shared
      demo: my-lab
      purpose: prod
    quota:
      limits.cpu: "4"
      requests.memory: 8Gi

# Sandbox API provides:
#   sandbox_openshift_namespace       = "sandbox-<guid>-user"    (primary)
#   sandbox_tools_namespace           = "sandbox-<guid>-tools"   (second, via var:)
#   sandbox_username / sandbox_password  — RHSSO user (keycloak: yes)
#   sandbox_openshift_api_url, sandbox_openshift_ingress_domain
#   cluster_admin_agnosticd_sa_token
#   cluster_admin_agnosticd_sa_token  = "<SA token>"
# For the second entry (name: tools):
#   sandbox_openshift_tools_namespace = "mylab-tools-<guid>"

Minimal workloads list

workloads:
  - my_collection.ocp4_workload_my_lab_setup
  - agnosticd.showroom.ocp4_workload_showroom

Variables from Sandbox API — Full Reference

These variables are automatically injected by Sandbox API into your AgnosticD run. You do not declare them — you only consume them in your role variables and templates.

Scheduler-Only variables (no namespace_suffix)

Variable Example value Description
sandbox_openshift_api_url https://api.cluster-abc12.example.com:6443 Cluster API endpoint. Used by k8s module and oc CLI.
sandbox_openshift_ingress_domain apps.cluster-abc12.example.com Wildcard ingress domain. Use to build Route hostnames and service URLs.
sandbox_openshift_console_url https://console-openshift-console.apps.cluster-abc12.example.com OpenShift web console URL. Useful for Showroom tabs and lab instructions.
cluster_admin_agnosticd_sa_token eyJhbGciOiJSUzI1NiIs... Cluster-admin SA token for AgnosticD. Never log or commit this value. Used automatically by the AgnosticD k8s connection.
No sandbox_openshift_namespace in Scheduler-Only When you use a single sandboxes: entry with no namespace_suffix, Sandbox API does not create a namespace. The variable sandbox_openshift_namespace will not be set. Your roles are responsible for creating their own namespaces.

Full Namespace API variables (with namespace_suffix)

Variable Example value Description
sandbox_openshift_namespace mylab-user-abc12 Primary namespace created by Sandbox API. Format: <catalog>-<suffix>-<guid>.
sandbox_openshift_api_url https://api.cluster-abc12.example.com:6443 Cluster API endpoint. Same across all sandbox entries for a given order.
sandbox_openshift_ingress_domain apps.cluster-abc12.example.com Wildcard ingress domain for the cluster.
sandbox_openshift_console_url https://console-openshift-console.apps.cluster-abc12.example.com OpenShift web console URL.
cluster_admin_agnosticd_sa_token eyJhbGciOiJSUzI1NiIs... Cluster-admin SA token. Never log or commit.
sandbox_username user-abc12 OCP local user account created by Sandbox API for this order.
sandbox_password (from RHDP vault) Password for sandbox_username. Comes from RHDP secret management — never hardcode.
sandbox_openshift_<name>_namespace sandbox_openshift_tools_namespace For additional sandbox entries (name != primary), the namespace variable is prefixed with the entry name. E.g., a sandbox named tools provides sandbox_openshift_tools_namespace.

The guid variable

Variable Example Notes
guid drw4x 5-character unique identifier for this order. Injected by AgnosticD, not Sandbox API. Use it to generate unique names: mcpuser-{{ guid }}.

Common Features

LiteMaaS — AI API Keys

LiteMaaS is the RHDP AI gateway that provides a unified OpenAI-compatible API in front of multiple LLM providers. You can create a per-tenant virtual API key using the ocp4_workload_litellm_virtual_keys role. The key is rate-limited by budget and duration so one tenant cannot exhaust shared capacity.

  • Role: agnosticd.ai_workloads.ocp4_workload_litellm_virtual_keys
  • The role sets litellm_virtual_key after creation — subsequent roles can reference this fact
  • Always set ocp4_workload_litellm_virtual_keys_catch_all: false on shared clusters. Setting it to true will attempt to delete all keys not owned by this tenant.
  • Budget is in USD. Set a per-order cap appropriate to your lab duration.
  • The admin key is a secret — use lookup('env', 'LITEMAAS_ADMIN_KEY'), never hardcode it.
catch_all: false is mandatory on shared clusters If ocp4_workload_litellm_virtual_keys_catch_all is true, the destroy playbook will delete ALL virtual keys on the LiteMaaS instance that were not created by this tenant. This will break every other tenant's AI API access. Always set it to false.

Showroom

Showroom is the RHDP tab-based UI framework. It displays a set of browser tabs to the lab attendee — typically a lab guide, an OpenShift console, and application URLs. It is deployed as a workload via the ocp4_workload_showroom role and is driven by a Git repository containing tab configuration.

  • Role: agnosticd.showroom.ocp4_workload_showroom
  • Configure showroom_git_repo and showroom_git_repo_revision in AgV
  • Pass per-tenant data through showroom_user_data — a dict of key/value pairs that become template variables in the Showroom content
  • Always the last workload in the provisioning list; always the first in the destroy list

Destroy behavior

The remove_workloads list in AgV determines which roles run during order destruction. This list must be in the reverse order of workloads. Each role's remove_workload.yml is called, which undoes what the corresponding workload.yml created.

Sandbox API handles cluster reclamation After all remove_workloads complete, Sandbox API reclaims the cluster (or namespace). You do not need to delete the cluster itself, only the per-tenant resources your roles created.

Common pitfalls

Pitfall Consequence Fix
Hardcoding a secret (token, password, API key) in AgV YAML Secret committed to Git; security incident Use lookup('env', 'VAR_NAME') or AgnosticD secret injection
Setting catch_all: true for LiteMaaS on shared cluster All other tenants lose their AI API keys on destroy Always catch_all: false
Wrong destroy order Resources left orphaned; cluster may not be reclaimable remove_workloads must be exact reverse of workloads
Using sandbox_openshift_namespace in Scheduler-Only pattern Variable is undefined; role fails In Scheduler-Only, use ocp4_workload_tenant_namespace_suffixes to define namespaces
Not setting ocp4_workload_tenant_keycloak_username consistently Roles use different usernames; resources get orphaned Define once at the top of common.yaml; all roles reference this single var
Forgetting to add Showroom to remove_workloads Showroom deployment left running after order expires Showroom must be first in remove_workloads
Using / in branch names Git ref ambiguity; CI pipeline may fail Use dashes only: my-feature-branch
