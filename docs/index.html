What is Sandbox API?

Sandbox API is the RHDP service that allocates OpenShift clusters (and other cloud resources) to lab orders. When a user requests a catalog item, the RHDP platform calls Sandbox API to provision a cluster from a pre-warmed pool, then hands control to AgnosticD (via AgnosticV configuration) to deploy the actual lab content.

Sandbox API does the following for every order:

  • Picks an available OpenShift cluster from the resource pool
  • Creates a service account with cluster-admin privileges for AgnosticD to use
  • Injects a set of well-known variables into your AgnosticD run (API URL, ingress domain, console URL, SA token)
  • Optionally creates namespaces and OCP user accounts (OCP Sandbox API pattern only)
  • Reclaims the cluster when the order is destroyed or expired

Sandbox API does not deploy your lab content. That is the job of AgnosticD roles configured through AgnosticV. The two patterns described in this guide differ in how much Sandbox API does versus how much your Ansible roles do.

Key insight In both patterns your AgnosticV common.yaml configures what runs, in what order, and with what variables. Sandbox API just gives you a cluster and injects variables. Everything else is up to your workloads — Ansible roles, GitOps, or both.

How Cluster Selection Works — cloud_selector

When you place an order, Sandbox API needs to pick a cluster from the pool. The cloud_selector in your __meta__.sandboxes entry is how you tell it which clusters are eligible. Understanding this is essential — a wrong or missing tag means your order will either fail or land on the wrong cluster.

The magic behind cluster selection Every cluster registered in the Sandbox API pool has a set of annotation tags (key-value pairs) stored in the database. Your cloud_selector is a filter — Sandbox API finds all clusters whose annotations contain every tag you specified. If a cluster has your tags (plus any others), it qualifies. From all qualifying clusters, Sandbox API picks one at random that has available capacity.

How it works — step by step

  1. You define cloud_selector tags in your AgV __meta__.sandboxes entry
  2. Sandbox API queries the cluster pool: "give me all valid clusters whose annotations contain ALL these tags"
  3. From the matching clusters, it picks one at random (weighted by availability and capacity limits)
  4. It creates a sandbox on that cluster, injects all variables into your AgnosticD run, and provisioning begins

Example cloud_selector

__meta__:
  sandboxes:
  - kind: OcpSandbox
    namespace_suffix: user
    cloud_selector:
      cloud: cnv-dedicated-shared   # cluster type — must match
      demo: mcp-with-openshift     # lab-specific tag — key and value set by admin at cluster registration
                                     # key name varies: could be "demo", "lab", or anything — ask admin
      purpose: prod               # prod vs dev pool
      keycloak: "yes"            # optional — only clusters with RHSSO installed

The cluster in the pool must have ALL four tags to qualify. A cluster tagged cloud: cnv-dedicated-shared + demo: mcp-with-openshift + purpose: prod but missing keycloak: yes will NOT be selected.

Variables injected after cluster selection

Once a cluster is selected, Sandbox API injects these variables into every AgnosticD role automatically. You do not declare them — you just use them:

VariableWhat it containsExample value
sandbox_openshift_api_url Cluster API server URL — use this to connect to the cluster https://api.cluster-xyz.example.com:6443
sandbox_openshift_ingress_domain Wildcard apps domain — use this to build Route hostnames and all service URLs apps.cluster-xyz.example.com
sandbox_openshift_console_url Web console URL — pass to Showroom for the console tab https://console-openshift-console.apps.cluster-xyz...
cluster_admin_agnosticd_sa_token Cluster-admin SA token — used by all roles to authenticate to the cluster. Never log or commit this value. eyJ... (JWT)
sandbox_openshift_namespace Primary namespace created by Sandbox API (from namespace_suffix). Format: sandbox-{guid}-{suffix} sandbox-abc12-user
sandbox_username / sandbox_password RHSSO user credentials — only provided when keycloak: "yes" is in cloud_selector sandbox-abc12 / generated
sandbox_openshift_ingress_domain is the most used variable Almost every service URL in your lab is built from this: https://myapp-{namespace}.{{ sandbox_openshift_ingress_domain }}. If you are missing this in your role variables or Showroom config, your URLs will be wrong. This variable is always available — you never need to look it up manually.

Why Sandbox API — Shared Clusters

The primary driver is Zero Touch OpenShift — the RHDP direction for customer and partner workshops where attendees get an instant, isolated OpenShift experience without waiting for a cluster to provision. The original pattern required a full dedicated CNV cluster per order, which is not compatible with that model.

Zero Touch OpenShift The goal is for a customer or workshop attendee to click "Order" and have a fully working OpenShift environment in minutes — not an hour. This is only possible with pre-provisioned shared clusters. The Sandbox API scheduler-only pattern is the foundation that makes this possible.
  • Speed. A dedicated CNV cluster takes 45–60 minutes to provision. A shared cluster order using Sandbox API takes 2–3 minutes — the cluster is already running, we are only provisioning the per-tenant resources. For event formats like Lightning Labs or booth demos where attendees walk up and want to start immediately, waiting an hour is not an option.
  • Scale across use cases — and Lightning Labs at Summit 2026. This pattern supports multiple deployment scenarios from a single catalog item: full workshop sessions, booth demos, and on-demand ordering from demo.redhat.com. A shared cluster pool can absorb concurrent demand across all of these without provisioning a dedicated cluster for each.

    At Summit 2026, the event team is introducing self-service labs called Lightning Labs — and this is expected to be one of the biggest attractions of the event. Lightning Labs are short, self-paced sessions that attendees can walk up and start on their own, with no instructor and no scheduled slot. For this to work, the environment must be ready in minutes. A dedicated CNV cluster per order (45–60 min) makes Lightning Labs impossible. The shared cluster + Sandbox API pattern makes them viable — an attendee orders, gets their environment in 2–3 minutes, completes the lab, and the environment is destroyed automatically. That cycle has to work at scale, concurrently, across the event floor. One dedicated cluster per order cannot do that.
  • Establishing a reusable pattern. This is the first lab in RHDP to use the shared cluster + Sandbox API scheduler-only pattern end-to-end. The goal is not just to ship this one lab — it is to prove out an approach that other labs can follow. The tenant roles (ocp4_workload_tenant_keycloak_user, ocp4_workload_tenant_namespace, ocp4_workload_tenant_gitea) were built to be generic and reusable, not tied to MCP. Any lab that needs to run on a shared OpenShift cluster can use the same building blocks.
  • Authentication. The original lab used HTPasswd with sequential usernames (user1, user2) because each order got its own cluster — HTPasswd made sense there. On a shared cluster that model breaks down: you cannot use sequential usernames across concurrent orders and you need a proper identity provider that can handle many users with isolated sessions. RHBK is already on the cluster; each order just adds one user to the existing realm and removes it on destroy. The auth model follows naturally from moving to shared clusters — it is not a goal in itself.
Three-Layer GitOps Architecture Shared cluster labs are built on a three-layer pattern: Infra (install operators once), Platform (create instances and configure once), Tenant (per order — the user). This is a general GitOps pattern, not specific to Sandbox API.

Which Pattern Should I Use?

There are two integration patterns. Choose based on who should own namespace and user lifecycle.

Scheduler-Only Summit 2026

Use when

  • Multiple tenants share one cluster
  • A cluster provisioner pre-installs shared services (Keycloak, Gitea, ArgoCD) once
  • Your Ansible roles create namespaces and users per-order
  • You need GitOps (ArgoCD) managing tenant workloads
  • You need LiteMaaS AI API keys per tenant
  • Complex multi-namespace topologies per tenant

Sandbox API does: Schedule cluster, provide token + domain

Your roles do: Create users, namespaces, repos, ArgoCD apps, everything else

Full guide →

OCP Sandbox API

Use when

  • Each order gets its own isolated namespace(s)
  • You want Sandbox API to own namespace + OCP user lifecycle
  • Simpler labs that deploy directly into sandbox namespaces
  • No shared cluster services needed
  • Single-team or single-namespace workloads
  • Less Ansible role complexity is acceptable

Sandbox API does: Schedule cluster, create namespaces, create OCP user, apply quota

Your roles do: Deploy lab content into the ready namespaces

Summit 2026 — Scheduler-Only Pattern

Sandbox API schedules a cluster and injects credentials. All per-tenant resources are created by your workloads — RHBK user, namespaces, Gitea instance, ArgoCD Applications. A separate cluster provisioner installs shared services once per cluster (RHBK, Gitea, ArgoCD, ToolHive).

Key AgV fields: single OcpSandbox entry under __meta__.sandboxes with alias, cloud_selector, and quota. No keycloak: yes — you manage users yourself.

OCP Sandbox API Pattern

Sandbox API creates the namespaces and an RHSSO user for each order. Your workloads deploy lab content into the ready-made namespaces. Simpler setup — no cluster provisioner, no Keycloak role, no Gitea role. Less flexibility.

Key AgV fields: one OcpSandbox entry per namespace with namespace_suffix. Add keycloak: "yes" to create an RHSSO user. Use cluster_condition: same('alias') to pin multiple namespaces to the same cluster.
