1. New Architecture — Three-Layer Workflow

The RHDP shared cluster lab model separates concerns into three distinct layers. A single physical cluster is provisioned once by an operator; a platform bootstrap layer installs monitoring and shared services; and each catalog order creates an isolated tenant environment via the Sandbox API and a set of Ansible roles.

3. What the Sandbox API Does

The Sandbox API is the RHDP scheduling layer for shared OpenShift clusters. When a user places a catalog order, the Sandbox API selects an available cluster from the pool and exports a fixed set of variables to AgnosticD. It does not install any workloads — that is AgnosticD's job.

  • Schedules a cluster — picks an available shared OCP cluster from the pool registered under the matching cloud_selector tag, marks it as in-use for the order duration.
  • Creates one namespace (always) — the Sandbox API always creates at least one namespace on the cluster (named after the order GUID). Additional namespaces can be requested but this is optional per approach.
  • Creates a Keycloak user (optional) — in Approach A, Keycloak user creation is handled by the ocp4_workload_tenant_keycloak_user role, not the sandbox API. In future approaches, the API may manage this directly.
Key Constraint The Sandbox API does not know about your application. It only knows about clusters and namespaces. All workload provisioning (Gitea repos, Keycloak users, ArgoCD apps, AI agents) is handled by AgnosticD roles that run after the sandbox API schedules a cluster.

4. Variables Provided to AgnosticD

The following variables are injected into the AgnosticD run automatically by the Sandbox API after a cluster is scheduled. They are available as Ansible facts throughout the workload roles.

Variable Example Value Description
sandbox_openshift_namespace guid-abc12 Primary namespace created by the sandbox API. Used as the base namespace for tenant workloads.
sandbox_openshift_api_url https://api.cluster.example.com:6443 OCP API server URL. Used for k8s_auth, kubernetes.core, and SA token auth.
sandbox_openshift_console_url https://console-openshift-console.apps.cluster.example.com Web console URL for the cluster. Surfaced in Showroom tabs and user-facing info.
sandbox_openshift_ingress_domain apps.cluster.example.com Wildcard ingress domain. Used to construct per-user Route hostnames (${USER}.${DOMAIN}).
cluster_admin_agnosticd_sa_token (JWT, never hardcoded) Service Account token with cluster-admin scope. Used by roles that need cluster-level access. Must never be written to files.
sandbox_openshift_user user-abc12 Username for the RHBK/Keycloak user created for this order. Also used as the Gitea username prefix.
sandbox_openshift_password (generated, from vault) Password for the Keycloak user. Set via the ocp4_workload_tenant_keycloak_user role.
Secret Handling cluster_admin_agnosticd_sa_token and sandbox_openshift_password are secrets. Never write them into AgnosticV YAML files. Always reference via {{ lookup('env', 'VAR_NAME') }} or from vault-injected extra vars.

5. Approach A — Scheduler Only Summit 2026

In Approach A, the Sandbox API is used only as a scheduler. The API assigns a cluster but does not create any additional namespaces beyond the default one. AgnosticD roles handle all namespace creation, Keycloak user setup, Gitea org creation, and ArgoCD bootstrapping. This is the approach used for the Summit 2026 MCP lab.

Note: The Sandbox API Always Creates at Least One Namespace Even in Approach A, the sandbox API creates the primary namespace (sandbox_openshift_namespace). Roles like ocp4_workload_tenant_namespace then create additional namespaces (e.g., -gitea, -agent, -librechat) on top of this base.

cloud_selector — How Cluster Scheduling Works

The cloud_selector field maps to a label on clusters registered in the Sandbox API pool. When an order is placed, the API finds a cluster tagged with ocp4-mcp-lab-shared that has capacity, assigns it, and exports the cluster variables. Multiple catalog items can share the same pool (same cloud_selector) and will be load-balanced across available clusters.

ArgoCD AppProject — Wildcard Configuration

# bootstrap-tenant/templates/appproject.yaml
# One AppProject per tenant — scoped to tenant namespaces only
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: "tenant-{{ guid }}"
  namespace: openshift-gitops
spec:
  description: "Tenant project for order {{ guid }}"
  sourceRepos:
    - "*"   # wildcard — allows any repo; lock down in production
  destinations:
    - server: "https://kubernetes.default.svc"
      namespace: "{{ guid }}-*"   # matches all namespaces for this tenant
  clusterResourceWhitelist: []     # no cluster-scoped resources from tenant
  namespaceResourceWhitelist:
    - group: "*"
      kind: "*"
Wildcard sourceRepos The "*" wildcard in sourceRepos allows ArgoCD to deploy from any Git repository. This is acceptable for lab environments where tenants are trusted. For production, restrict to specific repos.

6. Keycloak: Two Options

Lab environments on shared clusters need a Keycloak user for authentication into LibreChat, the AI agent UI, and OpenShift itself (if using RHBK as the OCP identity provider). There are two ways to provision this user:

Option Option A — Sandbox API Keycloak Option B — Bring Your Own RHBK
Who creates the user Sandbox API (automatic, built-in) ocp4_workload_tenant_keycloak_user role
RHBK host Managed by RHDP infra team Installed on shared cluster by provisioner role
Realm Sandbox-managed realm rhdp (configurable)
Username pattern Set by sandbox API config user-{{ guid }} (configurable)
Password Generated by sandbox API; available as sandbox_openshift_password Generated by role; exported as Ansible fact
Destroy Sandbox API deletes on order end Role destroy task deletes user from RHBK
Best for Simple setups; no cluster-installed RHBK Summit 2026 MCP lab (Approach A) — full control
Approach A uses? No — role manages user Yes — this is Approach A
Approach A Recommendation Use Option B (RHBK installed on cluster, role creates user) for Summit 2026. This gives full control over the realm configuration, client scopes, and user attributes. The RHBK admin credentials are managed via vault and injected as environment variables.

7. LiteMaaS Virtual Keys

LiteMaaS (the RHDP LiteLLM proxy service) issues per-order virtual API keys. These keys restrict which AI models a tenant can use, set rate limits, and are automatically deleted when the order ends. The ocp4_workload_litellm_virtual_keys role handles creation and deletion.

Critical: catch_all: false Always set ocp4_workload_litellm_virtual_keys_catch_all: false for shared cluster labs. If catch_all: true, the destroy task will attempt to delete ALL virtual keys — including keys belonging to other tenants on the same cluster. This is a data-loss risk. With catch_all: false, only the key created for this specific order (matched by alias guid) is deleted.

AgnosticV Configuration

# Workload definition in common.yaml
workloads:
  - ocp4_workload_litellm_virtual_keys

# Variable configuration
ocp4_workload_litellm_virtual_keys_litellm_host: "litemaas.rhdp.redhat.com"
ocp4_workload_litellm_virtual_keys_litellm_master_key: "{{ lookup('env', 'LITEMAAS_MASTER_KEY') | default('REPLACE_ME', true) }}"
ocp4_workload_litellm_virtual_keys_key_alias: "{{ guid }}"   # unique per order
ocp4_workload_litellm_virtual_keys_models:
  - gpt-4o
  - gpt-4o-mini
  - claude-3-5-sonnet
  - claude-3-haiku
ocp4_workload_litellm_virtual_keys_max_budget: 5.0           # USD per order
ocp4_workload_litellm_virtual_keys_budget_duration: "30d"
ocp4_workload_litellm_virtual_keys_catch_all: false           # REQUIRED for shared clusters

# Exported facts (set_fact by role — used downstream by gitops_bootstrap)
# litellm_virtual_key: "sk-vk-xxxx..."   (available as Ansible fact)
# litellm_virtual_key_id: 42             (used for deletion on destroy)

How the Key Is Passed to Tenant Apps

The ocp4_workload_litellm_virtual_keys role sets litellm_virtual_key as an Ansible fact via set_fact. The ocp4_workload_gitops_bootstrap role reads this fact when templating the Helm values file for the tenant AppSet. The value is written into a Kubernetes Secret in the tenant namespace, which LibreChat and the AI agent mount at runtime.

set_fact Ordering The litellm_virtual_keys role must run before gitops_bootstrap in the workloads list so that litellm_virtual_key is available when the Helm values template is rendered. Ordering in the workloads list is execution order.

8. ArgoCD Setup for Shared Clusters

Per-User ApplicationSet Names

Each tenant gets a uniquely named ArgoCD ApplicationSet: bootstrap-tenant-{guid}. This prevents collisions between concurrent orders on the same cluster. The name is deterministic and used by the destroy task to find and delete the correct AppSet. 

# ApplicationSet created by gitops_bootstrap role
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: "bootstrap-tenant-{{ guid }}"   # unique per order
  namespace: openshift-gitops
spec:
  generators:
    - list:
        elements:
          - guid: "{{ guid }}"
            namespace: "{{ sandbox_openshift_namespace }}"
            ingress_domain: "{{ sandbox_openshift_ingress_domain }}"
            keycloak_user: "{{ ocp4_workload_tenant_keycloak_user_username }}"
            gitea_org: "{{ guid }}"
            litellm_key: "{{ litellm_virtual_key }}"
  template:
    metadata:
      name: "{{ '{{guid}}' }}-{{ '{{app}}' }}"
    spec:
      project: "tenant-{{ guid }}"
      source:
        repoURL: "https://github.com/rhpds/ocpsandbox-mcp-with-openshift-gitops"
        targetRevision: main
        path: "apps/{{ '{{app}}' }}"
      destination:
        server: "https://kubernetes.default.svc"
        namespace: "{{ '{{namespace}}' }}-{{ '{{app}}' }}"
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=false    # REQUIRED — namespaces pre-created by role

CreateNamespace=false — Why This Matters

The CreateNamespace=false sync option is required for shared cluster labs. Namespaces are created by the ocp4_workload_tenant_namespace role with specific quota, LimitRange, and RBAC configured. If ArgoCD creates namespaces automatically, those constraints are absent, which can lead to resource exhaustion on the shared cluster.

Additionally, CreateNamespace=false ensures that if the ArgoCD AppSet is accidentally applied to an existing namespace, it does not reset namespace metadata.

Common Mistake Omitting CreateNamespace=false causes ArgoCD to create namespaces before the tenant_namespace role runs (on re-sync), which skips quota and LimitRange setup. Always set this option in the AppSet template.

9. Quota & LimitRange

Every tenant namespace must have a ResourceQuota and LimitRange to protect the shared cluster from resource exhaustion. The ocp4_workload_tenant_namespace role applies these automatically based on the variables you define in AgnosticV.

Shorthand Quota Format

# In common.yaml — shorthand format (role parses this)
ocp4_workload_tenant_namespace_quota:
  requests.cpu: "4"
  requests.memory: "8Gi"
  limits.cpu: "8"
  limits.memory: "16Gi"
  pods: "20"
  services: "10"
  persistentvolumeclaims: "5"
  requests.storage: "20Gi"

# LimitRange — defaults applied to containers without explicit limits
ocp4_workload_tenant_namespace_limitrange:
  default_request:
    cpu: "100m"
    memory: "256Mi"
  default_limit:
    cpu: "1"
    memory: "1Gi"
  max:
    cpu: "4"
    memory: "8Gi"
Warning: Do Not Use resources: {} If a Helm chart sets resources: {} (empty resources block), the LimitRange defaults will not apply. This causes pods to be scheduled without resource limits, which can consume unbounded CPU/memory on the shared cluster. Always set explicit resource requests and limits in your Helm charts, or use resources: null to let LimitRange defaults apply.

Quota and LimitRange are applied per-namespace. If you create multiple namespaces (e.g., gitea, agent, librechat), each gets its own quota. You can configure per-namespace overrides using the list format: 

# Per-namespace quota override
ocp4_workload_tenant_namespace_namespaces:
  - name: gitea
    quota:
      requests.memory: "4Gi"
      limits.memory: "8Gi"
  - name: librechat
    quota:
      requests.memory: "2Gi"
      limits.memory: "4Gi"
  - name: agent     # uses global default quota
  - name: mcp        # uses global default quota

10. Destroy Behavior

When an order ends, AgnosticD runs the destroy playbook. Each role's destroy tasks are executed in reverse order of the workloads list. The catch_all flag controls whether a role tries to clean up resources it did not create in this run (e.g., pre-existing namespaces passed in via variables).

Role catch_all: true (default) catch_all: false (shared cluster)
ocp4_workload_tenant_namespace Deletes ALL namespaces matching the prefix, even if they existed before the order Only deletes namespaces the role itself created (tracked via Ansible facts)
ocp4_workload_tenant_gitea Deletes the entire Gitea org and all repos unconditionally Deletes only if Gitea org was created in this run
ocp4_workload_tenant_keycloak_user Deletes user by username; may fail if user does not exist Deletes only if user was created in this run; skips gracefully if not found
ocp4_workload_litellm_virtual_keys Deletes ALL virtual keys — dangerous on shared clusters Deletes only the key with alias matching guid — safe for shared clusters
ocp4_workload_gitops_bootstrap Deletes all ArgoCD AppSets in the gitops namespace Deletes only bootstrap-tenant-{guid} — leaves platform AppSets intact
Always Use catch_all: false on Shared Clusters Without this setting, a destroy run on one tenant's order can accidentally remove namespaces, Gitea orgs, or LiteMaaS keys belonging to other concurrent tenants on the same cluster. This is the single most important configuration choice for multi-tenant shared cluster labs. 
# Set catch_all: false for all roles that support it
ocp4_workload_tenant_namespace_catch_all: false
ocp4_workload_tenant_gitea_catch_all: false
ocp4_workload_tenant_keycloak_user_catch_all: false
ocp4_workload_litellm_virtual_keys_catch_all: false
ocp4_workload_gitops_bootstrap_catch_all: false

11. Showroom Tab URLs

The Showroom tab displays lab instructions to the user. It also has "tabs" configured to open directly to the LibreChat UI, Gitea instance, and OpenShift console. Tab URLs use the per-user Route hostnames derived from the ingress domain. 

# showroom/ui-config.yml — tab configuration
# Variables substituted by the Showroom deployment role

tabs:
  - title: "LibreChat"
    url: "https://librechat-librechat-${USER}.${DOMAIN}"
    # expands to: librechat-librechat-user-abc12.apps.cluster.example.com
    icon: chat

  - title: "Gitea"
    url: "https://gitea-gitea-${USER}.${DOMAIN}"
    # expands to: gitea-gitea-user-abc12.apps.cluster.example.com
    icon: git

  - title: "OpenShift Console"
    url: "${OCP_CONSOLE_URL}"
    # expands to sandbox_openshift_console_url
    icon: openshift

  - title: "Agent UI"
    url: "https://agent-agent-${USER}.${DOMAIN}"
    icon: robot

# Variable substitution mappings (set in AgnosticV or Showroom role vars)
showroom_user_data:
  USER: "{{ sandbox_openshift_user }}"          # e.g. user-abc12
  DOMAIN: "{{ sandbox_openshift_ingress_domain }}"  # e.g. apps.cluster.example.com
  OCP_CONSOLE_URL: "{{ sandbox_openshift_console_url }}"
  GITEA_URL: "https://gitea.{{ sandbox_openshift_ingress_domain }}"
  LITECHAT_KEY: "{{ litellm_virtual_key }}"    # from litellm_virtual_keys role

The URL pattern librechat-librechat-${USER}.${DOMAIN} follows the convention: {service-name}-{namespace}-{username}.{ingress-domain}. The namespace is librechat-{username}, which is created by the ocp4_workload_tenant_namespace role. The Route hostname is constructed deterministically so Showroom can reference it without querying the cluster.

12. Common Pitfalls

# Pitfall Symptom Fix
1 Quota rejection on pod creation ArgoCD sync shows forbidden: exceeded quota; pods stay in Pending Increase ocp4_workload_tenant_namespace_quota values, or reduce Helm chart resource requests. Ensure LimitRange defaults are not overridden by resources: {}
2 set_fact not visible to downstream role gitops_bootstrap Jinja2 template fails with undefined variable: litellm_virtual_key Ensure ocp4_workload_litellm_virtual_keys is listed before ocp4_workload_gitops_bootstrap in the workloads list. Role ordering = execution ordering.
3 ArgoCD AppProject wildcard too restrictive Apps fail to sync with application repo not permitted Add the specific repo URL to sourceRepos in the AppProject, or use "*" for lab environments where security is acceptable.
4 ApplicationSet name collision Second order on same cluster overwrites first order's AppSet; first tenant's apps deleted Always include {{ guid }} in the ApplicationSet name: bootstrap-tenant-{{ guid }}. Never use a static name.
5 Showroom tab is blank / 404 Showroom tab opens but shows empty content or 404 Check that showroom_git_ref branch exists and the content/modules/ROOT/pages/ directory is present. Check Showroom pod logs for git clone errors.
6 Wrong namespace used by ArgoCD App deployed to openshift-gitops instead of tenant namespace Verify destination.namespace in the AppSet template is set to {{ '{{namespace}}' }}-{app} and not hardcoded. Ensure CreateNamespace=false is set.
7 LiteMaaS virtual key orphaned after destroy Destroy succeeds but LiteMaaS still shows old key; rate limit charges accumulate Confirm ocp4_workload_litellm_virtual_keys_catch_all: false and that the alias matches the guid. Check LiteMaaS API logs. Manually delete via POST /key/delete with the key ID if needed.

13. Future: CI-Based Cluster Onboarding

Today, onboarding a new shared cluster into the RHDP pool requires manual steps by the RHDP infrastructure team. The future goal is to make this self-service via the demo.redhat.com UI, with CI validating cluster readiness before it enters the pool.

Step Today (Manual) Future (Self-Service via demo.redhat.com UI)
Cluster registration Operator manually adds cluster to Sandbox API pool YAML and opens PR Admin submits cluster credentials via demo.redhat.com UI form; CI validates connectivity
Provisioner roles Operator runs AgnosticD provisioner playbook manually from laptop or AWX CI pipeline (Tekton or GitHub Actions) runs provisioner roles on cluster registration event
Validation Manual check: operators installed, RHBK accessible, ArgoCD healthy Automated test suite: checks operator status, ArgoCD sync, RHBK realm, Gitea API, Tekton pipeline run
Pool entry Manual PR merge to sandbox-api pool config Automatic after CI passes; cluster added to pool via API call
Capacity update Manual edit to pool config Cluster reports capacity automatically via metrics; auto-scaling rules apply
Decommission Operator removes cluster from pool YAML manually; drains orders Admin marks cluster for decommission in UI; Sandbox API drains orders gracefully, then removes from pool
Design Principle The CI-based onboarding model treats clusters as cattle, not pets. The provisioner playbook is idempotent, so re-running it on an existing cluster is safe and brings the cluster back to the desired state. The CI pipeline re-runs the provisioner on any detected drift.

14. Future: Sandbox Creates All Namespaces (Future / MCP Lab)

Not for Summit 2026 This section describes a future architecture where the Sandbox API creates all tenant namespaces directly, without the ocp4_workload_tenant_namespace role. This is being designed for post-Summit iterations and is not used in the Summit 2026 MCP lab. Summit 2026 uses Approach A (scheduler only) described in Section 5.

In this future model, the Sandbox API would become namespace-aware: instead of creating only one default namespace, it would accept a list of namespaces to create as part of the order specification. This would simplify the AgnosticD workload list and reduce the number of roles needed for a minimal setup.

Key Concepts for Future Namespace Model

  • Declarative namespace manifest — The catalog entry declares required namespaces in the AgnosticV common.yaml. The Sandbox API reads these and creates them before AgnosticD runs.
  • Pre-applied quota — Namespace quotas would be specified in the catalog entry and applied by the Sandbox API on namespace creation, eliminating the need for the tenant_namespace role in simple cases.
  • Role reduction — In simple labs, only two roles would be needed: ocp4_workload_gitops_bootstrap (to wire up ArgoCD) and ocp4_workload_showroom (for the lab UI). Namespace, Keycloak, and Gitea provisioning would be handled by the API layer.
  • Faster provisioning — Eliminating Ansible-based namespace creation reduces provisioning time by removing sequential API calls. The Sandbox API can create namespaces in parallel.
  • Destroy integration — When an order ends, the Sandbox API deletes all namespaces it created. No destroy tasks needed in AgnosticD for namespace cleanup.
  • Migration path — Labs using Approach A (tenant_namespace role) can migrate to this model without changing their GitOps charts — only the AgnosticV configuration changes.
