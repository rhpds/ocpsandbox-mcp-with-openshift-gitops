Three-Layer GitOps Architecture for Shared Cluster Labs

Infra / Platform / Tenant — a general pattern for any lab running on a shared OpenShift cluster

This pattern is not specific to the Sandbox API. It applies to any shared cluster lab where multiple tenants coexist on one cluster. The three-layer separation gives you clear ownership boundaries, predictable lifecycle, and clean destroy behavior.

Three-Layer Architecture: Infra / Platform / Tenant

Each layer has a clear owner, runs at a different frequency, and has a different lifecycle. Understanding this separation is essential before writing any AgV configuration or cluster provisioner playbook.

Layer Responsibility Runs How triggered MCP Lab example
Infra
Install Operators		 Install cluster-wide operators — no instances created yet, just the operators available Once per cluster cluster-provision.yml playbook — run manually (or via CI) when cluster is onboarded to the Sandbox API pool. See: cluster-provision.yml Installs: RHBK operator, Gitea operator, OpenShift GitOps (ArgoCD), Tekton (Pipelines), ToolHive, CloudNativePG. Creates infra, platform, tenants ArgoCD AppProjects.
Platform
Create Instances & Configure		 Create instances from installed operators, configure shared cluster services that all tenants will use Once per cluster — same one-time cluster provisioning as Infra ArgoCD syncs bootstrap-platform Application — created by infra bootstrap as part of the same cluster provisioning run Creates: Gitea server instance (from Gitea operator CR), enables user workload monitoring (Prometheus/Grafana for tenant namespaces). Future: shared LiteLLM instance, LDAP sync.
Tenant
The User		 Everything for one user's isolated environment — created fresh per order, destroyed when done Every order AgnosticD runs AgV workloads: list via Sandbox API scheduler Creates: one RHBK user, 6 namespaces, one Gitea instance (per-tenant, in user namespace), LiteMaaS virtual key. ArgoCD deploys: LibreChat, MCP servers (gitea + openshift), AI agent, Showroom.
Only the Tenant layer is in your AgV common.yaml The Infra and Platform layers are set up once by the cluster operator when a cluster joins the pool — they are not part of your catalog item. When you write a workloads: list in AgV, you are configuring only the Tenant layer. The operators and shared services are already there waiting.

How This Connects to the Sandbox API

The three-layer pattern maps directly onto the two main Sandbox API integration patterns:

  • The Sandbox API scheduler-only pattern maps directly to the Tenant layer. The Sandbox API does one thing: schedule a cluster and return a token and domain. Everything in the Tenant layer is done by your AgnosticD roles. See the Scheduler-Only guide.
  • Cluster Provisioner sets up the Infra and Platform layers once. A cluster-provision.yml playbook (separate from AgV) runs once per cluster when it joins the Sandbox API pool, installing all shared services (RHBK, Gitea, ArgoCD). After that, every order only touches the Tenant layer.
